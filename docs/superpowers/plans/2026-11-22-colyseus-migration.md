# Plan de implementación de Colyseus en PhaserQuest

> Para quien implemente el plan, usar `superpowers:executing-plans` o `superpowers:subagent-driven-development` y marcar cada paso al verificarlo.

**Objetivo.** Migrar el multijugador de PhaserQuest a Colyseus 0.18 con un mundo compartido, sincronización por proximidad y compatibilidad con los personajes guardados.

**Arquitectura.** Una instancia de `WorldRoom` administra las sesiones, los relojes y la distribución de estado. `GameServer` y sus entidades siguen resolviendo la simulación autoritativa, MongoDB guarda los personajes y `connection.ts` traduce mensajes y cambios de Schema a operaciones de la escena Phaser.

**Tecnologías.** Bun ≥ 1.3.10, Express 5, Vite, MongoDB, Phaser 4, `colyseus`, `@colyseus/sdk` y `@colyseus/ws-transport` de la línea 0.18, `@colyseus/schema` 5 y `bun:test`. Fijar las versiones exactas que pasen la primera tarea en `bun.lock`. [SDK TypeScript](https://docs.colyseus.io/getting-started/typescript) · [Versiones compatibles](https://docs.colyseus.io/migrating/0.18)

## Decisiones propuestas

| Enfoque | Consecuencia |
| --- | --- |
| Cambiar transporte y Schema en un solo paso | Entrega la arquitectura final antes, pero mezcla los problemas de sesión con los de visibilidad, combate y movimiento. |
| Migrar el transporte primero y el estado después **(propuesto)** | Los paquetes ya existentes sirven de puente temporal. Cada fase puede jugarse y revertirse con su versión de cliente y servidor. |
| Repartir las áreas del mapa en salas | Obliga a transferir jugadores, combates y objetos entre salas. Las 96 AOI del mapa actual ya son índices de proximidad dentro de un único mundo por proceso. |

- Crear `world` una sola vez desde el servidor con `matchMaker.createRoom('world', {})` y `autoDispose = false`. El navegador usa `client.join('world', { id })` o `client.reconnect(token)`. Restringir el matchmaker público a `join` y `reconnect` para impedir la creación de instancias adicionales. [Matchmaking](https://docs.colyseus.io/matchmaker) · [Configuración de salas](https://docs.colyseus.io/room)
- Conservar los ritmos iniciales de la simulación y la red, `1000 / 12` ms para el mundo, `2000` ms para regeneración y `200` ms para actualizaciones o parches. Conservar la predicción de clic y el pathfinding actual. [Reloj de sala](https://docs.colyseus.io/room/timing-events)
- Conservar la colección `players` y los campos `_id`, `name`, `x`, `y`, `weapon` y `armor`, así como las claves existentes de `localStorage`. Mantener los puntos de guardado actuales, incluida la restricción de grabar posición en exteriores. El ID de Mongo es la credencial de personaje heredada y queda fuera de Schema, chat, rutas URL y logs. El ID de entidad (`number`) y el ID de sesión de Colyseus (`string`) cumplen funciones distintas.
- Mantener `bun run dev` y `bun run start`, los flags `-p` y `--mongoPort`, `HOST`, `PORT`, `MONGODB_URI`, `MONGODB_DB`, los assets, `/phaser4.html` y Vite HMR. El primer ensayo valida WebSocket y HMR en el mismo origen sobre Bun. [Transporte WebSocket](https://docs.colyseus.io/server/transport/ws) · [Transporte nativo de Bun](https://docs.colyseus.io/server/transport/bun-websockets)

## Casos que deben quedar cubiertos

1. Dos pestañas intentan cargar el mismo personaje mientras la primera se desconecta o guarda. Sólo una sesión puede usarlo y el segundo intento conserva el personaje guardado. Tareas 2 y 3.
2. Se pierde la respuesta al crear un personaje, o el intento de borrar falla. El reintento de creación devuelve el mismo ID, y las claves locales sólo se limpian tras confirmar el borrado o la ausencia del personaje. Tarea 2.
3. Al cruzar AOI 0, un borde del mapa o una puerta que salta varios sectores, dos observadores ven altas y bajas correctas de avatares, monstruos y objetos. Tareas 4 y 5.
4. Un jugador o monstruo ya se está moviendo en la primera carga o al recuperar conexión. Su animación continúa desde la posición vigente y cada corrección de puerta o reaparición se aplica una sola vez. Tareas 4 y 5.
5. Un `path` malformado o una acción pendiente de la sesión anterior no modifica el mundo. Se conserva un jugador en movimiento tras un rechazo de input y se recupera la posición autorizada. Tareas 2 y 3.

## Tarea 2. Separar sesiones, persistencia y comandos del socket

**Archivos.** `server.js`, `js/server/GameServer.js`, `js/server/Player.js`, `js/server/CharacterStore.js` nuevo, `src/phaser4/connection.ts`, `shared/WorldProtocol.ts` nuevo, `test/characters.test.ts` y `test/world-commands.test.ts`.

**Interfaces.** `GameServer.handlePath(sessionId, { path, action, or }, latencyMs): boolean` toma acciones del tipo actual `0 | 3 | 4`. `CharacterStore` concentra creación, carga, guardado y borrado sobre la colección actual. `GameServer` lleva la reserva por `_id` durante apertura, sesión activa y cierre, con la misma exclusión para borrar.

- [ ] Probar con Mongo aislado que un documento anterior carga con sus coordenadas y equipo. Verificar dos aperturas simultáneas, borrado contra una apertura en curso, liberación tras la última escritura y distinción entre personaje ausente, activo y Mongo temporalmente inaccesible. Probar que repetir la misma creación devuelve el mismo `_id` y que el borrado repetido de un ID válido sigue confirmando la ausencia.
- [ ] Implementar `POST /api/characters` con `{ id, name }` y `POST /api/characters/delete` con `{ id }` para la pantalla inicial. Para un personaje nuevo generar 12 bytes aleatorios con `crypto.getRandomValues` en el navegador, guardar `{ id, name }` provisionalmente en `sessionStorage` y usar `$setOnInsert` por `_id`. Repetir `{ id, name }` devuelve `{ id }` y reutilizar un ID con otro nombre devuelve `409`. Borrar devuelve `{ ok: true }` si el personaje quedó ausente, `409` si está ocupado y `503` si Mongo falla temporalmente. Validar IDs de 24 caracteres hexadecimales y nombres recortados de 1 a 20 caracteres. Guardar el ID en `localStorage` al confirmar la creación, eliminar el intento provisional y conservar el personaje ante errores de conexión posteriores. Retirar los handlers Socket.IO de creación y borrado para que las dos operaciones pasen por la misma ruta de persistencia.
- [ ] Probar rutas vacías, un recorrido de 61 tiles, coordenadas fuera de mapa, valores no enteros, saltos, colisión y payloads inválidos para ataque o cofre. Aceptar una ruta de un tile sólo para interacción y conservar las orientaciones `1` a `4`. Validar la forma antes de indexar el mapa. La sesión identifica al jugador y el dominio valida las acciones y decide su efecto.
- [ ] Hacer que Socket.IO llame a estas interfaces y conservar sus paquetes y la respuesta `reset` para movimiento rechazado. Serializar los guardados pendientes por personaje y esperar su finalización antes de liberar la reserva, con la política de checkpoints actual. Ejecutar las pruebas nuevas y el smoke de creación, movimiento, recarga y borrado con `MONGODB_DB=phaserQuest_smoke`.

## Tarea 3. Pasar el juego completo a `WorldRoom`

**Archivos.** `server.js`, `js/server/WorldRoom.ts` nuevo, `js/server/GameServer.js`, `js/server/MovingEntity.js`, `js/server/Item.js`, `shared/WorldProtocol.ts`, `src/phaser4/connection.ts`, `test/colyseus-bootstrap.test.ts` y `test/world-room.test.ts`.

**Interfaces.** El navegador usa `Client` de `@colyseus/sdk` y conserva `savedCharacter()` y `createConnection()`. Los mensajes de entrada son `ready`, `path`, `revive`, `chat` y `ponq`. El puente envía `init`, `update`, `reset` y `chat` con los objetos actuales, serializados por Colyseus. En errores de entrada distingue personaje ausente, personaje ocupado y error transitorio.

- [ ] Escribir pruebas con dos SDK reales para verificar mismo `roomId`, avatares distintos, chat de proximidad, rechazo de doble sesión, reconexión y liberación de reserva. En una reconexión rápida comprobar que el ID de entidad se conserva y que se vuelve a recibir una vista completa aunque los vecinos hayan cambiado.
- [ ] Arrancar Mongo y esperar la lectura del mapa antes de admitir jugadores. Registrar y crear `world` una vez. `onJoin` asocia el `sessionId` con un personaje y cancela el alta si el cliente se fue mientras cargaba. `ready` inicializa al cliente después de que éste registre sus handlers. `onCreate` configura `setTimestep` a `1000 / 12` ms para que avance el reloj de sala, con regeneración y publicación de paquetes a sus cadencias. Usar `room.clock` para los `setTimeout` de juego con sus demoras actuales, y cancelar los temporizadores en `onDispose`. Cerrar Vite, la sala y Mongo ordenadamente. [Timestep de Colyseus 0.18](https://docs.colyseus.io/netcode/server-input)
- [ ] En `onDrop` reservar asiento durante 10 segundos. El avatar y el combate siguen simulándose durante esa ventana y los comandos quedan bloqueados hasta reanudar. Después de vencer el plazo o salir voluntariamente, limpiar avatar, combate y reserva una sola vez en `onLeave`. Guardar en `sessionStorage` el `reconnectionToken` por personaje, actualizarlo al reconectar y usar la carga normal si expiró. Al reanudar el puente, pedir un `init` nuevo y repoblar las AOI actuales. Bloquear `move`, `revive` y `chat` durante la caída. Probar la reconexión antes y después de los 5 segundos de conexión inicial, y comprobar que la cola del SDK queda vacía con `room.reconnection.maxEnqueuedMessages = 0`. [Reconexión del SDK](https://docs.colyseus.io/sdk/connection)
- [ ] Sustituir Socket.IO en cliente y servidor conservando las notificaciones de UI. Tras `ready`, medir latencia con el `ponq` actual y usarla para el inicio de rutas como hasta hoy. Ejecutar `bun test`, `bun run typecheck`, `bun run build` y probar con dos perfiles que se ven, caminan, cruzan una puerta, chatean, luchan y reconectan. Conservar este punto como versión jugable de retorno.

## Tarea 4. Sincronizar jugadores y vida con Schema

**Archivos.** `js/server/WorldState.ts` nuevo, `js/server/WorldRoom.ts`, `js/server/GameServer.js`, `js/server/GameObject.js`, `js/server/MovingEntity.js`, `src/phaser4/connection.ts`, `src/phaser4/protocol.ts`, `src/phaser4/WorldScene.ts`, `src/phaser4/main.ts` y `test/world-state.test.ts`.

**Interfaces.** `WorldState` expone `online` como número de jugadores conectados, `players` como `MapSchema` con claves `String(id)` y `self` como `MapSchema` con claves `sessionId`. Cada `PlayerState` contiene los datos visibles de `PlayerSnapshot`. `SelfState` contiene `playerId` y `life` y sólo entra en la vista de su dueño. Usar el constructor `schema()` y `.view()` en las colecciones filtradas. [Definición de Schema](https://docs.colyseus.io/state/schema) · [Vistas por cliente](https://docs.colyseus.io/state/view)

- [ ] Probar que clientes de AOI no contiguos reciben su propio `SelfState`, jamás el de otro jugador, y sólo reciben avatares dentro de su AOI y las adyacentes. Probar alta al entrar, baja al salir y reingreso sin duplicado, incluyendo entidad de ID `0`, bordes del mapa y teletransporte largo. Al recargar o reconectar, la vida llega desde la vista inicial.
- [ ] Proyectar al estado desde el dominio y actualizar pertenencia a `StateView` usando `AOI.entities` y `shared/AOIutils.ts`. Actualizar sólo las vistas afectadas por altas, bajas o cambios de área. Calcular adyacencia con límites válidos de fila y columna y comprobar que `0` se trate como AOI previa válida. Mantener la simulación como única autoridad de posición, combate e inventario.
- [ ] En `connection.ts`, registrar `Callbacks.get(room)` y aplicar altas, bajas y cambios agrupados por parche. Esperar al registro privado `self` y al primer estado sincronizado antes de inicializar la escena. Adaptar la escena al alta y baja explícita de avatares. Actualizar la interpolación remota al iniciar o cambiar una ruta y aplicar correcciones sólo donde corresponda a puerta, revivir o reinicio. Representar de forma explícita borrar `route` y `targetID`, incluido el objetivo `0`. [Callbacks del SDK](https://docs.colyseus.io/state/callbacks)
- [ ] Suprimir jugadores, vida y contador del `update` temporal. Dejar en el puente monstruos y objetos. Enviar `reset` para corrección y `revived` con su posición. Entregar `hp`, `killed`, `used` y `noPick` en `playerEvents`, un mensaje privado que conserva todos los eventos del tick y sale después del parche correspondiente. Al reconectar, reconciliar la vida y la posición sin repetir efectos visuales o logros antiguos. Correr las pruebas y verificar vida, chat, muerte y reaparición en dos perfiles.

## Tarea 5. Sincronizar monstruos y objetos, retirar el puente

**Archivos.** `js/server/WorldState.ts`, `js/server/WorldRoom.ts`, `js/server/GameServer.js`, `js/server/AOI.js`, `js/server/GameObject.js`, `js/server/MovingEntity.js`, `js/server/Player.js`, `js/server/PersonalUpdatePacket.js`, `src/phaser4/{connection,protocol,WorldScene,MonsterView}.ts`, `test/world-state.test.ts`, `test/world-room.test.ts`, `package.json`, `bun.lock`, `README.md` y `AGENTS.md`.

**Interfaces.** Completar `WorldState` con `monsters` e `items` como `MapSchema` filtrados, con los campos visibles de `MonsterSnapshot` e `ItemSnapshot`. Phaser aplica altas, cambios y bajas por colección. Los monstruos conservan su ruta completa y los jugadores remotos su destino. La versión de ruta cambia sólo al iniciar, reemplazar o terminar una ruta.

- [ ] Ampliar las pruebas a monstruos que entran o salen durante un recorrido, cofres que se abren, loot que desaparece, equipo, reaparición y dos golpes antes del mismo parche. Verificar que ambos golpes se entregan y que entrar a mitad de movimiento sitúa la animación en el tramo actual. Probar que cada sprite se elimina al salir de AOI y que la escena deja de recibir callbacks de una sesión cerrada.
- [ ] Conectar las dos colecciones al mismo índice espacial y eliminar sprites al recibir `onRemove` de Colyseus. Mantener en los mensajes chat, corrección, reaparición y eventos puntuales. Cambiar `ponq` a un sondeo independiente del estado para conservar la estimación de latencia también cuando no hay parches. Confirmar que se mantiene la predicción al caminar y la cámara al entrar y salir por puertas.
- [ ] Repetir el recorrido y la carga de la tarea 1 sobre el build Colyseus. Registrar bytes, CPU y p95 de publicación en las mismas condiciones. Si el p95 alcanza los 200 ms de cadencia, o el p95 de publicación, CPU o ancho de banda supera en más de 20 % la medición Socket.IO, investigar antes de retirar el puente. Empezar por mutaciones redundantes y trabajo por vista. `StateView` agrega trabajo de codificación por vista. [Coste de StateView](https://docs.colyseus.io/state/view) · [Herramientas de carga](https://docs.colyseus.io/tools/loadtest)
- [ ] Retirar `init` y `update` del puente, `js/server/UpdatePacket.js`, `js/server/Encoder.ts`, `src/Decoder.ts`, `shared/CoDec.ts` y `test/codec.test.ts` cuando las pruebas de sala y estado cubran sus flujos. Quitar `socket.io` y `socket.io-client` de las dependencias y regenerar `bun.lock`. Mantener `AOIutils` y `spaceMap` como infraestructura espacial. Actualizar comandos y arquitectura en `README.md` y `AGENTS.md`.
- [ ] Correr `bun install --frozen-lockfile`, `bun test`, `bun run typecheck` y `bun run build`. En producción y con dos perfiles, verificar alta y carga de un personaje anterior, movimiento local y remoto, puertas y cámara, monstruos, combate, loot, cofre, muerte, reaparición, chat, caída breve, expiración, recarga, borrado y reinicio del servidor. Comprobar que sólo queda una sala y que el navegador carga el bundle y los assets del mismo release.

## Cambio de versión y vuelta atrás

Cerrar cada tarea con su propia revisión y commit una vez verificada. Para desplegar, arrancar una sola versión del mundo contra la base de producción, publicar su bundle junto al servidor y forzar recarga de clientes con la versión anterior. Para volver atrás, detener la versión nueva, esperar el cierre de sus escrituras y levantar el último par cliente-servidor verificado apuntando a la misma colección. Probar la vuelta atrás sobre una copia de Mongo con un personaje creado bajo Colyseus y otro guardado antes del cambio.

En esta revisión pasaron `bun test`, `bun run typecheck` y `bun run build` sobre la versión Socket.IO. La prueba de compatibilidad Bun, Vite y Colyseus, el smoke con Mongo y la comparación de carga forman parte de las tareas de implementación.
